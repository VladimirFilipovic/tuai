The Memo That Stopped tuai Lagging

A chat TUI that re-syntax-highlighted its entire history ten times a second — and the one cache key that taught it to stop.

refreshViewport
rebuilds the scrollback string, then re-pins it to the bottom. Called on every tick.
renderMessages
turns the whole message slice into styled text — markdown, chroma, shading.
the hot path
spinner ticks (~10/s while streaming) + every stream chunk, each calling the two above.
the memo
a cached render of the persisted messages, rebuilt only when its key changes.

1 · The symptom

The complaint was plain: "tuai becomes slow in longer conversation, scrolling and everything is slow." Short chats felt instant; long ones turned to molasses. The tell-tale shape — cost that grows with conversation length — pointed at work being repeated over the whole history rather than just the new bytes.

2 · Where the time went

Every visual refresh ran through one function, renderMessages(), which walked the entire session.Messages slice and rebuilt each bubble from raw text:

  • chroma tokenised and 24-bit-coloured every fenced code block,
  • regex passes restyled **bold** and `inline code`,
  • wordwrap reflowed every prose line, and
  • shadeBubble ran an SGR-reset regex over every line of output.

None of that is cheap — and it ran on a slice that, for the persisted messages, is identical from one frame to the next. The trigger fired constantly:

// spinner ticks: re-render the viewport each frame to animate the dot
if _, ok := msg.(spinner.TickMsg); ok {
    if !m.streaming { return m, nil }
    m.spin, spCmd = m.spin.Update(msg)
    m.refreshViewport()        // ← re-renders ALL messages, ~10×/sec
    return m, spCmd
}

So with N messages in the buffer, a single streaming reply paid roughly 10 × N full markdown renders per second. Cost grew linearly with the conversation — exactly the lag the user felt.

3 · The fix, in one picture

Persisted messages are immutable: they change only when one is appended (or the whole buffer is cleared). So re-styling them on every tick is pure waste. The new renderStaticMessages() renders that block once and hands back a cached string until a small key says otherwise:

func (m *chatModel) renderStaticMessages(wrap, bubbleInner int) string {
    key := fmt.Sprintf("%d|%d|%s|%t",
        len(m.session.Messages), wrap, CurrentTheme().Name, isDark())
    if key == m.staticKey {
        return m.staticCache    // hot path: a map-key compare, nothing more
    }
    // … rebuild every bubble exactly once, then:
    m.staticCache = b.String()
    m.staticKey   = key
    return m.staticCache
}

4 · Why those four fields are the whole key

The key has to capture every input that can change how an immutable message draws — and nothing else, or the cache thrashes.

key fieldchanges when…why it matters
len(Messages)a turn is sent / received, or /clearthe only way the persisted set mutates
wrapthe terminal is resizedword-wrap width changes every line
theme.Name/theme picks a palettechroma + bubble colours change
isDark()/light · /dark · /autolight/dark swaps the whole palette
Why count is enough: no code path ever mutates an existing entry — sendMessage, the stream-done handler, and persistTools all only append; /clear sets the slice to empty. So a changed message set always shows up as a changed length.

5 · What still re-renders — on purpose

The live tail — the spinner line, in-flight thinking, streaming tool blocks, and the growing pending reply — still renders on each refresh. That's correct: it's the one part actually changing mid-stream, and it's a single message's worth of work, not the whole history.

1
renderMessages pulls the static block from cache. A string the model already holds — concatenated, not recomputed.
2
It appends a blank separator, then renders only the live tail. Bounded by the current turn, independent of conversation length.
3
On done, the reply is appended → count changes → key misses once. The freshly-finished message folds into the cache for all future frames.

6 · The result

Streaming ticks and keystrokes went from O(N) per frame to O(1) per frame in history length. The expensive markdown work now runs once per message instead of ten times a second forever. Build is clean; the UI tests pass unchanged, confirming the output is byte-for-byte the same — just computed far less often.
